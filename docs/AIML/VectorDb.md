VectorDb are designed to bridge the **semantics gap** between the traditional way how computers traditionally store data and how humans understand it.

Limitation of traditional db.

Relational db stores the data in structured field using the metadata or manually added tags. It works for basic queries and does not capture the nuanced, multi dimentional nature of undtructured data like the image, text and audio. Example - A relational db might find the images tagged "orange" and it will not find images similar to the color palette or complex landscape features.

In conventional structured databases like SQL, searching requires exact keyword matches or complex formatting. For example, a search for "clothing" in an employee handbook might fail to return results if the policy is titled "dress code," because SQL does not understand that these terms are related. This puts the burden on the user to use the exact terminology stored in the database.

### How the VectorDb works?

Vector databases shift this burden to the system by storing the meaning (semantics) of words rather than just their literal values.   
Vector Embeddings - Vector databases represents unstructured data as vector embeddings and they are mainly an array of numbers where each position represents a learned feature of the data.

Semantic Proximity - In the vector space, the similar items are positioned close together and the dissimilar items are far apart. It allows the database to perform similarity searches as mathematical operations.

Creating Embeddings - These vectors are generated by embedding models (like Clip for images, GloVe for text, or Wav2vec for audio) that have been trained on massive datasets. Data is run through an embedding model (such as all-miniLM-L6-v2) which converts text into a long vector of numbers. These vectors allow semantically similar words, like "holiday" and "vacation," to share a similar mathematical space even if they share no common letters. The data passes through the model's layers, it extracts increasingly abstract features—such as edges in an image or context and meaning in text.


Dimensionality: To capture nuances like tone, formality, and sentiment, these vectors use hundreds or thousands of dimensions . For instance, one dimension might represent the topic while another captures the sentiment.

Efficiency and Speed - In real-world systems deal with millions of vectors containing hundreds or thousands of dimensions, comparing a query to every single vector would be too slow. Vector databases solve this through vector indexing using **Approximate Nearest Neighbor** (ANN) algorithms - **HNSW** (Hierarchical Navigable Small World) Creates multi-layered graphs to connect similar vectors. **IVF** (Inverted File Index) Divides the vector space into clusters and only searches the most relevant ones. These methods trade a small amount of accuracy for significant improvements in search speed

### Core application of VectorDb.

One of the most prominent uses of vector databases is in Retrieval Augmented Generation (RAG). In RAG, the database stores document chunks as embeddings. When a user asks a question, the system finds relevant text by comparing vector similarity and feeds that information to a large language model (LLM) to generate an accurate response.

Setting up a vector database involves several critical technical considerations for accurate retrieval - Scoring and Similarity: The system uses mathematical methods like cosine similarity to determine how closely a query matches the stored data. Scoring thresholds are set to filter results; high thresholds (e.g., 0.7) ensure high-confidence matches, while lower thresholds (e.g., 0.3) allow for weaker associations.

Chunking and Overlap - Large documents are broken into smaller "chunks" before being stored. Chunk overlap is necessary to ensure context is preserved and to prevent words from being split in half, which would destroy their semantic meaning.
